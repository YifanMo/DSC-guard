# Broad Search Strategy for Oracle-Consumption Failure Dataset

## Overview

The current five MVP incidents are treated as a seed set. We use them to derive three rule families and search a larger indexed blockchain surface without downloading full-chain data locally.

The resulting dataset is two-tiered:

- **Index-level candidate dataset**: broad candidates found by remote indexed queries, stored as compact rows with trigger transactions, evidence tiers, closure reasons, and impact summaries.
- **Seed/evaluation dataset**: the five MVP cases are fixed, already-materialized rows used to evaluate the rule families.
- **Local evidence dataset**: only evidence-tiered remote candidates are materialized into local receipts, decoded logs, replay traces, and semantic validation reports.

This design lets the paper describe broad historical coverage while keeping paid API usage bounded.

Default chain scope is the validated seed-chain scope: Ethereum, BNB Chain, Avalanche, Base, and Scroll. These are the chains represented by the five replayable MVP incidents, with Ethereum kept as the reference mainnet ecosystem. Arbitrum, Optimism, and Polygon are excluded from default experiments unless explicitly requested.

## Pipeline

1. **Seed rule extraction**
   - Feed-binding seeds: Ploutos and Rho.
   - Price-composition seed: Moonwell cbETH.
   - Freshness-handling seeds: Venus LUNA and Blizz LUNA.
   - Output: `artifacts/broad_search/rules.json`.
   - Seed rows are rendered to `artifacts/broad_search/seed_candidates.jsonl` with `dataset_layer=seed_evaluation` and `already_materialized=true`; they never enter the local download queue.

2. **Rule-based broad search**
  - Render-only Dune SQL templates are generated by:

     ```bash
     python scripts/render_broad_search_queries.py --start 2022-01-01 --end 2026-05-12 --chains ethereum,bnb,avalanche,base,scroll
     ```

  - SQL templates are written to `artifacts/broad_search/sql/`.
  - Candidate-index SQL is intentionally not top-k limited. The deprecated `--top-k` argument is ignored; downstream materialization is controlled only by evidence-closure gates.
   - The render script does not execute Dune queries and does not use paid APIs.

3. **Dune shard execution**
   - Execute the broad index query set by stage. Calibration must pass before full execution:

     ```bash
     python scripts/run_broad_dune_queries.py --stage calibration --split-by month,chain,rule --performance medium --resume --max-execution-credits 5 --max-total-credits 50 --output-dir artifacts/broad_search/dune_exports/calibration_binding_closure
     python scripts/run_broad_dune_queries.py --stage full --start 2022-01-01 --end 2026-05-12 --chains ethereum,bnb,avalanche,base,scroll --split-by month,chain,rule --performance medium --resume --output-dir artifacts/broad_search/dune_exports/full_mvp_chains_2022_20260512
     ```

   - Each shard writes `query.sql`, `manifest.json`, and paginated result exports.
   - `--resume` skips completed shards and prevents duplicate Dune credit use.
   - `--stop-on-cancel` stops scheduling later shards after the first failed or cancelled shard.
   - The runner writes the Dune `execution_id` to the shard manifest immediately after submit, before polling completes, so long-running jobs remain externally auditable and cancellable.
   - Stage credit guards are enforced by the runner by default: calibration `5` credits/shard, pilot `10`, full `20`. Use `--no-credit-limit` only for explicitly approved Dune count/index experiments; it does not loosen RPC materialization budgets.

4. **Single-chain experiment path**
   - Before running the full dataset, a single-chain end-to-end experiment can validate the operational loop on Avalanche R3:

     ```bash
     python scripts/run_single_chain_broad_experiment.py --dry-run --max-shards 2
     python scripts/run_single_chain_broad_experiment.py --execute-dune --resume --stop-on-cancel
     python scripts/run_single_chain_broad_experiment.py --ingest --materialize-dry-run
     ```

   - Default output is `artifacts/broad_search/single_chain/avalanche_2022_20260512/`.
   - Default rule is `freshness_handling_failure`; R1 feed-binding remains deferred for later cost-specific optimization.

5. **Evidence-Closure Triage**
   - Candidates are not ranked by heuristic weights.
   - Each candidate is assigned one evidence tier:

     | Tier | Meaning |
     |---|---|
     | `A_replayable` | Trigger, oracle anomaly, lending impact, actor, temporal order, and replayable semantic constraint are all observable. |
     | `B_high_confidence_incomplete` | Trigger, oracle anomaly, lending impact, and temporal order are observable, but actor/source/replay fields are incomplete. |
     | `C_remote_anomaly_only` | Trigger and oracle anomaly are visible remotely, but lending impact is not closed. |
     | `reject_out_of_scope` | Non-lending, lacks oracle-consumption relation, lacks temporal order, or belongs to an excluded class. |

   - Within each tier, display order is deterministic, but it is not a selection or truncation rule:

     ```text
     has_replayable_constraint DESC
     has_actor DESC
     trigger_to_impact_seconds ASC NULLS LAST
     impact_usd_known DESC
     impact_tx_count DESC
     source_quality_rank ASC
     ```

6. **Evidence materialization**
   - All `A_replayable` candidates enter the local queue.
   - `B_high_confidence_incomplete` candidates enter only when the fixed gate holds: lending impact, temporal order, source quality rank `<= 2`, impact transaction count `> 0`, and trigger-to-impact interval inside the class window.
   - `C_remote_anomaly_only` candidates stay in the remote index unless later evidence closes the lending-impact loop.
   - If the queue is too large, tighten semantic gates and rerun preflight; do not apply top-k, weighted scores, or amount-based cutoffs.
   - For each local candidate, download the minimal causal trace: one trigger receipt and the first causal impact receipt(s).
   - Use verified source/ABI only when semantic extraction is required.
   - Do not run broad RPC `eth_getLogs` scans.

7. **Candidate ingestion**
   - Dune exports are ingested locally with:

     ```bash
     python scripts/ingest_broad_search_results.py --input-dir artifacts/broad_search/sample_exports
     ```

   - Outputs:
     - `artifacts/broad_search/candidates_full.jsonl`
     - `artifacts/broad_search/candidate_summary.json`
     - `artifacts/broad_search/materialization_queue.jsonl`
     - `results/broad_search_coverage.md`

8. **Semantic validation**
   - Convert materialized evidence into `artifacts/log_trace/{case}.jsonl`.
   - Run `scripts/verify_trace.py --case {case}`.
   - Keep validated candidates in results; mark unvalidated remote candidates as index-level candidates only.

9. **Auto-tuning loop**
   - Use the story-scope driver to run count-only preflight and gate-only download planning:

     ```bash
     python scripts/auto_tune_broad_search.py --target-local-bundles 3000
     python scripts/auto_tune_broad_search.py --execute-dune --no-credit-limit --target-local-bundles 3000 --resume
     ```

   - Outputs:
     - `results/story_scope_counts.md`
     - `results/story_scope_download_plan.md`
     - `results/story_detection_summary.md`
     - `artifacts/broad_search/auto_tune_story_scope/auto_tune_manifest.json`

## Rule Families

### R1: Feed-Binding Failure

Search for historical lending-protocol candidates where an asset-to-price-source binding change is observable, the normalized asset/feed identities are inconsistent or incomplete, and same-protocol lending impact follows.

Seed behavior:

- `USDC -> BTC/USD`
- `ETH/address(0) -> WBTC/USD`

General evidence closure:

- `lending_surface`: identify lending markets from decoded lending state-transition calls such as supply/mint, borrow, repay/redeem, withdraw, and liquidation.
- `protocol_cluster`: keep oracle/admin, market token, and lending contracts in the same protocol cluster before impact is considered.
- `binding_change_candidates`: find decoded oracle/price/feed/source/aggregator/asset binding changes; selector matches are fallback metadata, not the dataset scope.
- `asset_feed_identity`: normalize observed asset and feed labels into comparable identities such as `USDC`, `ETH`, or `BTC`.
- `same_protocol_impact`: require subsequent same-protocol lending impact; token transfers are reserved for local evidence slices rather than the primary broad query.

Local materialization:

- Trigger oracle-config receipt.
- Up to five follow-up supply/borrow/liquidation receipts.
- Optional verified source/ABI for the oracle config contract.

Cost rule:

- Query starts from decoded lending surface and protocol-cluster evidence closure. It does not use manually selected block ranges, and it does not treat explicit selector lists as the primary search scope.

### R2: Price-Composition Failure

Search for derivative-asset oracle wrapper or governance updates where formula operands may be missing, then look for liquidation or borrow activity.

Seed behavior:

- `cbETH/USD` expected as `cbETH/ETH * ETH/USD`, but actual consumption used only `cbETH/ETH`.

Local materialization:

- Governance or oracle-wrapper trigger receipt.
- Up to eight liquidation or borrow receipts.
- Verified oracle wrapper/source if available.

Cost rule:

- Query starts from derivative lending markets and inventory-linked oracle/governance contracts.

### R3: Freshness-Handling Failure

Search for same-account lending closures where collateral supply/deposit is followed by non-collateral borrow outflow, then associate the impact with the latest prior Chainlink `AnswerUpdated` for the collateral identity.

Seed behavior:

- LUNA feed stopped near lower-bound values while Venus and Blizz continued to accept LUNA collateral.

Local materialization:

- Last `AnswerUpdated` or stale marker receipt.
- Up to one supply receipt and one borrow receipt for selected candidate accounts.
- Optional protocol market ABI if decoded indexed tables are unavailable.

Cost rule:

- Query starts from lending market impact and only then joins prior `AnswerUpdated` logs. The feed does not need to be labelled as part of the protocol.

## Cost Controls

- Dune broad search is remote and compact; local artifacts store only candidate rows and evidence slices.
- RPC is reserved for known transaction receipts, not open-ended scans.
- Explorer APIs are used only for verified source/ABI of selected candidates.
- Candidate-index SQL includes partition filters but does not impose a default `top_k` limit, so remote coverage summaries are not confused with local download limits.
- The local materialization queue is capped separately, after evidence-tier filtering.
- Dune shard execution supports `--resume`; repeated runs do not re-execute completed shards.
- The local materialization queue is filtered by evidence tier before any receipt download.
- Default remote-candidate download caps are minimal: R1 `1+1`, R2 `1+2`, R3 `1+2` receipt bundles. Full transaction lists remain compact remote fields unless manually promoted.

## Safety Boundary

- The project only queries historical logs, receipts, decoded events, verified source, and indexed transfer data.
- It does not send transactions, call contract write methods, use private keys, or simulate attack execution.
- It does not generate steps for exploiting a live protocol or predict future targets.
- The broad search is framed as historical dataset construction and semantic validation for known failure classes.

## Paper Wording

Recommended wording:

> We use the five manually validated incidents as a seed set to derive three protocol-agnostic search rules. These rules are evaluated over chain-indexed event tables to construct a broad candidate dataset. To control cost, candidates are triaged by evidence closure, and only those with sufficient historical trigger, impact, actor, temporal-order, and replay evidence are materialized locally for semantic validation.

Avoid claiming:

- We downloaded all chain data.
- We exhaustively discovered all oracle attacks.
- Chainlink feed logs alone are sufficient.
